先说结论：**绝大多数普通编码场景，你感受不到提升，完全可以删掉；我讲清楚二者适用边界，你自行决定取舍。**

## 1. sequential-thinking（顺序思考 /thinking MCP）

### 它什么时候有用

1. 大型架构设计、多方案对比、复杂故障根因排查
    
2. 需要强制模型分步拆解、防止一步跳跃漏条件（例如设计 TradeFlow 命名规范、整体架构、CI 流程）
    
3. 需求逻辑高度复杂、多约束叠加场景
    

### 它什么时候几乎没用（你日常 90% 工作）

- 写接口、修复 bug、写组件、调试 TS 类型、写 ast-grep/biome 配置
    
- 短小功能开发、单行代码、查询文档
    

> 弊端： 每次调用会额外消耗一轮工具往返，增加延迟；简单任务反而拖慢速度。 很多时候模型本来就能分步思考，不需要强制调用工具。

### 实操建议

**方案 A（推荐，兼顾性能）：直接从全局删掉。** 只在偶尔做大架构设计的时候，临时在项目`.mcp.json`加上，用完移除。 **不要常驻全局**，日常编码收益极低。

## 2. memory MCP（本地持久记忆）

原理：本地一个 sqlite，AI 主动写入知识点，跨会话记住约定。

### 真实短板（也是你感觉不到提升的根本原因）

1. **主动权在 AI 手上！AI 想起来才会去查询记忆，不会自动检索。** 你存了命名规范、架构规则，AI 经常忘记主动调用 memory 读取。
    
2. 记忆库缺乏自动索引，内容一多，检索命中率暴跌；
    
3. 容易存入大量无效垃圾信息，干扰后续对话；
    
4. 你已经可以通过 `CLAUDE.md` 固定项目级规则（优先级更高，强制生效）。




#### 什么时候 memory 勉强有用

长期持续同一个大型项目、反复重申同一套标准（像你的 TradeFlow 命名规范），并且你持续**主动提醒 AI：重要规则写入 memory，开工先读取 memory**。

#### 最终评估

如果你懒得持续提醒 AI、不想维护记忆库，**直接删除完全不亏**。 替代方案：

- 全局通用约束 → 写进全局 settings 系统提示
    
- TradeFlow 项目专属规范 → `CLAUDE.md`（强制加载，比 memory 可靠得多）
    

## 五、我的实操建议（贴合你的开发模式）

### 推荐精简后的全局 MCP 清单（移除 thinking + memory）

```json
"mcpServers": {
  "everything-search": {},
  "fetch": {},
  "tavily": {},
  "ultracite": {}
}
```

#### 调整策略

1. sequential-thinking：移出全局。需要架构推演时，项目内临时启用。
    
2. memory：直接永久移除。改用 `CLAUDE.md` 固化项目规范，可控、稳定、零工具开销。
    

### 配套下发给 AI 的最终工具调度规则（存入 [CLAUDE.md](CLAUDE.md)）

```Plain
## 工具调度强制规则
1. 禁止调用内置 WebSearch；全网检索必须使用 tavily MCP
2. 已知网页内容读取：优先 fetch MCP，禁止内置WebFetch；网络异常兜底使用Bash curl
3. 本地文件查找：everything-search
4. 代码符号、跨文件引用查询：codegraph（项目MCP）
5. 官方库文档优先查询 context7（项目MCP）
6. 复杂架构多步骤分析场景，手动启用 sequential-thinking，日常不主动调用
7. 所有模型流量经过火山方舟网关；MCP网络请求直连
```

## 补充取舍总结一句话

> thinking、memory 属于**增益型工具，不是刚需工具**。 刚需工具：文件检索、网页抓取、搜索、代码分析； 非刚需：记忆、分步思考。感受不到正向收益就大胆删除，减少 MCP 进程数量、降低启动开销、减少工具选择混乱。
