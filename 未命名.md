1. 概念重复：同一个工具（如 utils）既在"自用软件"中有用途说明，又有独立的知识体系
     2. 维护困难：修改一个地方，其他地方忘记同步
     3. 关系混乱："体"（概念本质）与"用"（应用场景）交织在一起

    科学管理方案：体用双链架构

    📐 核心设计原则

     1 体 (Essence) → 是什么、定义、原理、核心概念
     2 用 (Application) → 在什么场景下、如何使用、解决什么问题

    🔄 一改全改的机制

    1. 单一事实源 (Single Source of Truth)


    ┌───────────────┬─────────────┬────────────────────────────┐
    │ 信息类型      │ 存放位置    │ 引用方式                   │
    ├───────────────┼─────────────┼────────────────────────────┤
    │ 工具/概念定义 │ 0-体/       │ 其他地方用 [[概念名]] 引用 │
    ├───────────────┼─────────────┼────────────────────────────┤
    │ 个人配置      │ 1-自用软件/ │ 引用体 + 我的差异化配置    │
    ├───────────────┼─────────────┼────────────────────────────┤
    │ 场景解决方案  │ 3-场景/     │ 组合引用多个体             │
    └───────────────┴─────────────┴────────────────────────────┘


    2. 变更传播流程

     1 当 Mise 升级新功能时：
     2 1. 只修改 `0-体/工具/Mise.md`
     3 2. 所有引用 `[[Mise]]` 的地方自动获得最新定义（通过双链）
     4 3. 个人配置文件中只写与默认配置的差异

    3. 关系图谱查询

    利用 Obsidian 的图谱视图：
     - 反向链接：查看哪些场景使用了某个工具
     - 图谱分析：发现过度耦合的节点

    📝 实施步骤

    第一阶段：建立"体"层
     1. 创建 0-体/ 文件夹及子目录
     2. 迁移现有核心概念（Git、HTTP、Vim 等）
     3. 每个文件只写不随时间变化的本质

    第二阶段：重构"用"层
     4. 修改现有文件，删除重复定义
     5. 用 [[体/概念名]] 替换内联解释
     6. 只保留个人配置和场景化用法

    第三阶段：建立场景层
     7. 创建 3-场景/ 文件夹
     8. 按问题域组织（而非工具域）
     9. 每个场景文件是"体"的组合应用

    第四阶段：自动化维护
     10. 使用 Obsidian 插件（如 Dataview）自动生成索引
     11. 定期检查孤立节点（无引用的文件）
     12. 建立变更检查清单

     13. Dataview - 自动聚合引用关系
     14. QuickAdd - 快速创建带模板的体/用文件
     15. Various Complements - 自动补全双链
     16. Obsidian Query Table - 可视化关系表

    这个方案的核心优势：
     - ✅ 一改全改：定义只在"体"层，双链自动同步
     - ✅ 关系清晰：体用分离，场景独立
     - ✅ 易于扩展：新工具只需在"体"层添加，场景层自动可引用
     - ✅ 降低维护成本：个人配置只写差异部分
