# 团队协作场景

> 场景描述：多人协作开发项目，管理代码合并、代码审查和版本发布

## 问题背景

团队协作时常见的问题：
- 代码冲突频繁
- 代码质量参差不齐
- 发布流程混乱
- 责任追溯困难

## 解决方案

### 核心工具组合

| 工具/概念 | 作用 | 配置差异 |
|----------|------|---------|
| [[Git版本控制]] | 版本管理 | 使用 Git Flow 工作流 |
| GitHub/GitLab | 代码托管 | 使用 PR/MR 机制 |
| ESLint/Prettier | 代码规范 | 统一团队配置 |
| CI/CD | 自动化检查 | 自动运行测试和 lint |

### 步骤 1：Git 工作流设计

```
main (生产分支)
  ↑
develop (开发分支)
  ↑
feature/* (功能分支)
```

### 步骤 2：分支命名规范

```bash
# 功能分支
feature/user-login
feature/payment-integration

# 修复分支
fix/login-bug
fix/typo

# 发布分支
release/v1.0.0
```

### 步骤 3：提交信息规范

```bash
# Conventional Commits 格式
<type>(<scope>): <subject>

# type 类型
feat: 新功能
fix: 修复 bug
docs: 文档更新
style: 代码格式（不影响代码运行）
refactor: 重构
test: 测试相关
chore: 构建工具/依赖管理

# 示例
feat(auth): 添加用户登录功能
fix(api): 修复用户接口空指针问题
```

### 步骤 4：Pull Request 流程

```bash
# 1. 从 develop 创建功能分支
git checkout develop
git checkout -b feature/user-login

# 2. 开发完成后推送到远程
git push origin feature/user-login

# 3. 在 GitHub 创建 PR
# - 填写详细描述
# - 关联 Issue
# - 请求 Review

# 4. 根据 Review 修改
git commit -m "refactor: address review comments"

# 5. 合并到 develop
# - Squash and Merge（推荐）
# - 或 Rebase and Merge
```

### 步骤 5：代码审查清单

- [ ] 代码是否符合规范（ESLint/Prettier）
- [ ] 是否有适当的测试覆盖
- [ ] 是否有不必要的复杂逻辑
- [ ] 变量命名是否清晰
- [ ] 是否有安全隐患
- [ ] 是否有性能问题

## 常见问题

### 问题 1：代码冲突

```bash
# 拉取最新代码
git fetch origin
git rebase origin/develop

# 解决冲突后
git add .
git rebase --continue
```

### 问题 2：误提交敏感信息

```bash
# 立即撤销提交
git reset --soft HEAD~1

# 如果已推送，强制推送
git push --force
```

### 问题 3：合并错误的分支

```bash
# 撤销错误的 merge
git reset --hard HEAD~1

# 重新合并
git merge <correct-branch>
```
